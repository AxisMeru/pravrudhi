# G0: real SFT trainer + generation adapter for the 1.13B Megatron-Core line

Code-only until the lead says "GPU is yours". Nothing here has been run on a
GPU. `python3 -m py_compile` has been run on every file in this directory (no
torch needed) and passes.

## Files

- `collate.py` -- torch-free prompt-masked byte-level collation. Tested by
  `tests/test_collate.py` (11 tests, runs on the host with plain `pytest`,
  no torch, no `/trackB` mount).
- `train_megatron_sft.py` -- real SFT trainer for `data/checkpoints/m4/final.pt`
  (1.13B Megatron-Core NemotronH). Saves a checkpoint in the M4 blob layout
  and verifies it by reloading + one forward pass at the end.
- `generate_megatron.py` -- batched greedy generation + `sequence_nll`, same
  `load_model / generate / sequence_nll / linear_module_names` contract as
  `model_io.py` (the 370M adapter), so `evaluate.py` can switch models by a
  flag.
- `lora_megatron.py` -- `GenericLoRA` + `inject_lora_generic`: a
  not-`nn.Linear`-specific extension of `ttt.py::inject_lora`/`LoRALinear`
  for Megatron's `ColumnParallelLinear`/`RowParallelLinear`/TE `Linear`
  layers. Does not edit `ttt.py`.

## seq_len decision: 1536, not 512

`configs/train/nemotron_h_1b.yaml`'s `train.seq_len: 4096` is the model's
actual positional cap (`max_sequence_length` passed into Megatron's
`MambaModel`, `position_embedding_type="none"`). The dry run's `seq_len=512`
was a VRAM-measurement choice, not an architectural limit. Grounded prompts
run ~1.0-1.35 kB + target <= 220 B (up to ~1.57 kB = ~1.57k bytes = ~1.57k
tokens, byte-level). `--seq-len` defaults to **1536**: comfortably under the
4096 cap, large enough to avoid truncating nearly all grounded examples. The
mandatory preflight step (below) is what actually certifies this fits in
VRAM for the container-and-batch-size combination used on a given run --
1536/512 = 3x the proven batch-4/seq-512 dry run's 23.8 GiB is a rough
ceiling to preflight against, not a re-derived certainty.

## Padding decision: fixed-length (seq_len - 1), for training only

Batches are padded to the **fixed** shape `seq_len - 1`
(`collate.collate_ids(..., pad_to_fixed_len=True)`, the trainer's only mode),
mirroring `pad_to_fixed_len=True` in the proven dry run
(`runs/g0_expandable/dry_run_1p13b_batch4.json`: batch 4, seq_len 512, 40/40
steps, peak VRAM 23.8 GiB, no OOM) rather than `sft_megatron_batched.py`'s
own default (pad to each batch's own max length). The dry run's own comments
record why: Megatron/Transformer-Engine/Triton appears to cache a compiled
kernel per distinct sequence *shape*, so a run whose batches are collated to
a different length each time keeps adding cache entries and its VRAM climbs
-- the failure mode the earlier (non-fixed-length) SFT attempt hit. Fixed
shape is the only configuration actually measured OOM-free at this model
size, so the real trainer reproduces it.

This is safe specifically **for training**, and specifically because
`StructuredNemotronH.forward` always calls Megatron's `MambaModel` with
`attention_mask=None` -- there is no attention-mask/padding-mask input at
all on this model's forward path, fixed-length or otherwise (confirmed by
reading `eval_adapter.py`; every call site in this codebase, including
`sft_megatron_batched.py` and `scripts/m7/generate.py`, passes
`attention_mask=None` unconditionally). Mamba2's recurrence runs
independently per batch row, so a padded row's trailing pad bytes can only
ever affect that same row's own masked (`-100`) loss positions -- never
another row's hidden state or loss, and never a still-to-be-predicted
position within the same row (padding only ever comes after the real
content, never before it).

**Generation is different and does NOT pad at all** -- `generate_megatron.py`
groups prompts by exact length instead, exactly like `model_io.py::generate`
and `scripts/m7/generate.py::group_by_length`. Padding a prompt (even
right-padding) before the still-to-be-predicted next byte would inject fake
context into that row's recurrent state and corrupt every subsequent
generated byte for it -- there's no masked-loss position downstream to
absorb the damage the way there is in training.

## LoRA injectability finding

`ttt.py::inject_lora` matches `isinstance(module, nn.Linear)`. That is
correct for Track B's 370M custom-loop `NemotronH` (confirmed: plain
`nn.Linear` throughout, per `model_io.py::linear_module_names`'s own
docstring). It is very likely **wrong** for the 1.13B Megatron-Core model:
`StructuredNemotronH.core` is a `megatron.core.models.mamba.MambaModel`
built from `mamba_stack_spec`, whose linear projections are Megatron-Core's
own `ColumnParallelLinear`/`RowParallelLinear` (or transformer-engine
`Linear`, depending on the spec's submodule choices) -- `nn.Module`
subclasses with their own `weight`/`bias`, not `nn.Linear` subclasses. This
is standard Megatron-Core/TE knowledge, **not independently verified against
this checkpoint's actual module tree** (`megatron.core` is a container-only
dependency; no GPU/container access during this write-up). Two concrete
consequences: (1) `isinstance(module, nn.Linear)` will match zero modules
here, making `ttt.py::inject_lora` (unmodified) a silent no-op on this model;
(2) Megatron's parallel linear layers commonly return a `(output,
output_bias)` tuple, not a bare tensor. `lora_megatron.py` (new file, does
not edit `ttt.py`) provides `GenericLoRA` + `inject_lora_generic`, matching
on any module with a plain 2-D `.weight` (excluding `nn.Embedding`) instead
of a specific base class, and its wrapper's `forward` handles both a tensor
and a `(tensor, bias)` return from the base. **Should be smoke-tested inside
the training container** (the import-only check below, then the first real
run) before being trusted for a TTT adaptation loop -- this has not been run
against a live `MambaModel`.
