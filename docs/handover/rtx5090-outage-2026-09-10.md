# RTX 5090 Workstation Outage — Diagnosis & Corrective Action

**Date:** 2026-09-10
**Host:** `ss@192.168.0.204` (`ss-Fusion-75`) — RTX 5090 training workstation, reached via `rtx5090-connect` skill
**Symptom reported:** SSH session kept "reconnecting" without ever succeeding; user's other Claude Code session was stuck in a reconnect loop.

## What was observed

1. `connect_check.sh` had succeeded cleanly earlier in the day (SSH fine, GPU confirmed RTX 5090, container up, GPU at 20GB/32GB used).
2. Later, both SSH (port 22) **and** SMB (port 445) stopped responding at the application layer:
   - ICMP ping: 0% packet loss, normal round-trip time — network path fine.
   - Raw TCP connect to ports 22 and 445: succeeded instantly (`nc -vz` confirmed handshake completes).
   - SSH/SMB protocol banner: never arrived, even after 30s, across many repeated attempts (verified with `ssh`, `nc`, and a raw Python socket read).
3. Port scan for out-of-band management (IPMI 623, web UI 80/443, VNC 5900, RDP 3389) found nothing — this is a consumer desktop, not a server with a BMC. No remote recovery path existed once sshd/smbd stopped responding.
4. The "reconnecting" behavior in the other session was actually a stuck reconnect loop: it could always re-establish the TCP connection (kernel-level accept), but the application-level handshake never completed, so it looked like it was perpetually "trying again" rather than truly failing.
5. User performed a hard power-cycle. Post-restart, SSH/Docker/GPU all responded normally again (GPU back to 36MiB used, confirming the previous training state was wiped by the reboot).

> **Reviewed on the target itself, 2026-09-10, by the pravrudhi session.** The mechanism below is confirmed
> and the corrective action has been applied — with three corrections and one addition. See
> **§Review findings** before acting on anything in this document.

## Root cause (confirmed via `sar` historical logs, `/var/log/sysstat` on the target)

**Memory overcommit → swap-thrashing collapse**, not a network issue and not GPU OOM.

| Time | %iowait | run-queue size | 15-min load avg | swap pswpout/s |
|---|---|---|---|---|
| 10:50 AM | 0.2% | 5 | 0.87 | 0 |
| 11:00 AM | 7.4% | 1 | 5.01 | 188 (spike begins) |
| 11:40 AM | 31.5% | 4 | 37.9 | 5.2 |
| 11:50 AM | 48.4% | **35** | 69.4 | 12.2 |
| 12:22 PM | 79.2% | 4 | **217** | — |
| 1:12 PM | 80.8% | **41** | **218** | — |
| 1:48 PM | — | — | `LINUX RESTART` | — |

- ~~`kbcommit` rose to ~64GB against only 30GB physical — i.e. ~160% overcommit.~~ **Corrected on review:**
  `%commit` was already **146.9% at 00:10**, hours before any load, and sits there all night. Overcommit is
  this box's baseline, not the anomaly, so it does not discriminate. The real signal is `kbmemfree`
  collapsing to **~260MB** from 11:50 onward and never recovering, with `%memused` 61% → 82%.
- `kbmemfree` collapsed to near zero from ~11:50 AM onward and stayed there.
- CPU time was consumed almost entirely by iowait (processes blocked on swap I/O), not real compute — the box wasn't "busy training," it was thrashing.
- This level of thrashing (run-queue 40+, load avg 200+) is severe enough that even lightweight daemons like `sshd`/`smbd` couldn't get scheduled promptly enough to write their protocol banners, even though the kernel's TCP/ICMP stack (lower-overhead, partly interrupt-driven) kept responding — which is exactly the "TCP connects, but the handshake never finishes" signature observed.
- It did not recover on its own over ~2.5 hours; only the hard power-cycle cleared it.

### Contributing factors

- **This is a shared desktop, not a dedicated headless GPU box.** A full GNOME session, WiFi, Bluetooth,
  GNOME Remote Desktop and a `transmission-daemon` coexist with ML jobs on 30GB of RAM.
- **Nothing had a memory ceiling** — neither the `train` compose service nor, more importantly, the job
  runner that was actually executing (see §Review findings).
- **No out-of-band recovery path exists** (no IPMI/BMC), so once host daemons are starved a hard power-cycle
  is the only fix.

## Review findings (added on the target, 2026-09-10)

The mechanism above is right and well evidenced. Three claims are not.

**1. The attribution was wrong. It was pravrudhi's own study, not another project's training job.**
The report attributes the load to "a single runaway job (or several concurrent ones)" and cites a job
directory listing naming `pranava`, `kinetic_exp10` and others. That listing is stale artefacts: every
`pranava-*` container on the host shows `Exited (0) 7 weeks ago`. Nothing from that project ran.

What did run, continuously across the whole window, was this repository's `apps` noise-floor study — kernel
job directories timestamped 10:48, 10:50, 11:18, 11:21, 11:26, 11:29, 11:33, 11:38, 11:40, 11:41, 13:10,
13:11 — overlapping with a `docker build` doing large `pip install`s (`transformers`, `lm-eval`, `evalplus`),
a full 2,160-test suite, a 240-call vendor-CLI panel, and out-of-process APPS scoring. **No single runaway
job: a pile-up of concurrent heavy work, none of it bounded.** The agent driving that session launched four
or five of those at once, which is the proximate cause and belongs in the record.

That changes the fix. A ceiling on the compose container would not have prevented this outage, because the
compose container was idle throughout. `pravrudhi_kernel/sandbox/runner.py` — the path that ran — had no
memory limit at all, and the report does not mention it.

**2. `systemd-oomd` is already installed, active and enabled.** Item 4 recommends the user install or enable
it. It is running (`systemctl is-active` → `active`, `is-enabled` → `enabled`) and it did not act, because by
default it only kills within cgroups that opt in via `ManagedOOMMemoryPressure`/`ManagedOOMSwap`, which
Docker's cgroups do not. Nothing was OOM-killed during the outage — confirmed, no kernel OOM messages — which
is precisely why the host thrashed for 2.5 hours instead of shedding load. So this is a configuration
question, not an installation one, and it needs the user only if they want oomd extended to the Docker slice.

**3. `mem_limit: 20g` was the wrong number, because caps have to compose.** 20g for the compose container
plus 20g for a pravrudhi job is 40GiB of ceilings on a 30GiB host: each looks prudent alone and together they
reproduce the outage. Both are set to **12g**, summing to 24 of 30 and leaving the desktop and OS ~6GiB.

One further caveat, unresolved: the `train` service uses `ipc: host`, so shared-memory pages it touches are
not cleanly confined by its own cgroup. The cap is still worth having; it is not airtight for shm-heavy jobs.

## Corrective action — **APPLIED 2026-09-10** (except items 3 and 4, see below)

### 1. Cap the training container's memory (primary fix)

**Applied**, at 12g rather than 20g (see §Review findings 3), to the `train` service in
`~/rtx5090setup/docker/docker-compose.yml`:

```yaml
    mem_limit: 12g
    memswap_limit: 12g   # == mem_limit: no swap headroom, fail fast instead of thrashing
```

Verified: `docker inspect` reports `Memory=12884901888 MemorySwap=12884901888`; the container came back up
with the GPU still visible. It was idle when applied (only `sshd` and `sleep`).

### 1b. Cap pravrudhi's own job runner (the path that was actually running) — **applied**

The gap the original report missed. `JobSpec` now carries `mem_gib` (default 12.0) and `pids_limit` (default
512), and `run_job` passes `--memory`, `--memory-swap` (equal, so a job fails rather than thrashes) and
`--pids-limit`. The default is a real number, not `None`: unlimited-unless-set would reproduce this the first
time someone forgot, and forgetting is what happened. Verified end to end — a job asking for 2GiB inside a
1GiB cap exits **137** (cgroup SIGKILL) instead of swapping, and a job that fits still exits 0.

Rationale: caps the container well below the 30GB installed RAM, leaving headroom for the desktop session and OS. A runaway job now gets OOM-killed *inside the container* (a normal, recoverable failure) instead of taking the whole host down. `memswap_limit == mem_limit` means the container gets no extra swap allowance, so it fails fast rather than sliding into slow thrashing.

Apply with:
```bash
scp docker-compose.yml ss@192.168.0.204:~/rtx5090setup/docker/docker-compose.yml
ssh ss@192.168.0.204 "cd ~/rtx5090setup/docker && docker compose up -d"
```
(A timestamped backup of the current `docker-compose.yml` has already been made on the target: `docker-compose.yml.bak-<timestamp>`.)

**Caveat:** this recreates the `train` container. No job was running at review time, but confirm nothing is in flight before applying, since `docker compose up -d` will restart it.

### 2. Pre-flight health check — **applied, in the kernel rather than in `submit_job.sh`**

`run_job` is the single chokepoint every container job passes through, so the gate lives there:
`host_pressure()` reads `/proc/meminfo` and `/proc/loadavg` (not a subprocess — the check runs precisely when
the host is struggling to schedule processes) and `run_job` raises `HostUnderPressure` rather than starting.

Thresholds are calibrated against this outage, not guessed: **MemAvailable < 2GiB** (normal hours on this box
are 7.5–8.2GiB; 11:50 was 1.29GiB) or **load1 > 4×CPU** (normal 0.1–3.1 on 16 CPUs; the window reached 143
then 215). Both fire inside the outage window and neither fires on a healthy host — checked live:
`24.63GiB available, load 0.05 over 16 CPUs`.

An aborted study is cheap next to a power-cycle, which wiped the study anyway. `submit_job.sh` belongs to the
other project's flow and is on the Mac side; it still wants the same gate.

### 3. Update the skill's troubleshooting section — **NOT DONE, cannot be done from here**

Document this failure signature explicitly in `SKILL.md` so a future session recognizes it immediately instead of re-deriving it from scratch:

> If SSH (and typically SMB/other host services too) accept the TCP handshake instantly but never send their protocol banner/response — even though ICMP ping is clean — this is host-level swap-thrashing collapse, not a network problem. Confirm via `sar -q` / `sar -r` / `sar -W` history (if reachable) showing high run-queue size, %iowait, and swap pageout activity. There is no out-of-band management interface on this box, so if it's already collapsed, a hard power-cycle is the only recovery — but the goal of this skill's memory limits and pre-flight checks is to prevent reaching that point at all.

### 4. Host-level proactive OOM protection — **re-scoped: already installed, needs configuration**

`systemd-oomd` is active and enabled (§Review findings 2). It did nothing because Docker's cgroups do not opt
into `ManagedOOMMemoryPressure`. Extending it to the Docker slice is a `sudo` change and therefore the user's
call; the container caps and the pre-flight gate above are the defence that does not need it. Installing
`earlyoom` is not needed and would duplicate what is already there.

## What this cost

The power-cycle wiped the `apps` noise-floor study mid-run (rotation 0 seed 2 of 9, at 13:11) and killed a
`mypy` run. Both are restartable and were restarted; the study's earlier rotations are not reusable because a
floor is the variance of one uninterrupted set of runs. No ledger rows were lost — the study writes its floor
only on completion, so nothing partial was recorded, which is the behaviour you want here.
